## Problem

ImpulseLock evaluates financial transactions in real time against a user's own behavioral preferences — a daily spending limit, a night-spending restriction, a sensitivity level, and a list of restricted categories — and returns one of three decisions: ALLOW, DELAY, or BLOCK, each with a risk score and a human-readable explanation of which rules fired.

It started as a four-person college project (Java/Spring Boot backend, React frontend, MySQL) that worked, but was built to demonstrate a concept, not to survive contact with real engineering standards. The goal for this rebuild was to take that working prototype and turn it into something that could actually hold up under the kind of scrutiny a software engineering interview — or a real production deploy — puts on a codebase.

## Why It Was Hard

The V1 codebase had no authentication, raw JDBC with hand-written SQL instead of a real persistence layer, hardcoded CORS and database credentials, a `main()` method that doubled as a demo script, and zero tests. None of that is unusual for a college project — but every one of those gaps is exactly what a senior engineer or interviewer would probe first.

Rebuilding it meant migrating the entire persistence layer from raw `JdbcTemplate` calls to Spring Data JPA + Hibernate, with Flyway owning schema migrations and Hibernate deliberately locked to validate-only (`ddl-auto=validate`) so the schema is never silently mutated at runtime. It meant adding real authentication and authorization (JWT, Spring Security, BCrypt, role-based access control for USER/ADMIN), audit logging via an AOP aspect that records every login, registration, transaction evaluation, and admin action, an admin dashboard for managing users and tuning rule weights live, transaction history with pagination/filtering/search, and a full DTO/mapper layer (MapStruct) so entities never leak past the service boundary — all without breaking the existing rule engine's behavior, since that decision logic was the one piece of V1 that was already sound.

Deploying it on entirely free infrastructure turned out to be its own engineering problem, not just a formality. Free-tier constraints forced real distributed-systems tradeoffs: cross-origin cookie behavior (`SameSite=Strict` silently drops refresh tokens across different domains), database provisioning quirks (a managed free MySQL tier that doesn't let you name your own database), and CI/CD paths that can silently diverge from each other.

## Approach

The rebuild followed a deliberate phase structure rather than a feature free-for-all: a full read-only engineering audit of the existing codebase first (architecture, technical debt, security gaps, a clear "already implemented / partially implemented / missing" breakdown against the target feature set) before a single line of production code changed. From there, every feature was proposed, approved, implemented, and explained individually — plan first, one feature at a time, never batched — with a Git history that reflects that discipline rather than one giant rewrite commit.

Deployment went out on a genuinely free stack: Render (Docker-based backend), Aiven (managed free MySQL), and Vercel (the React frontend), connected through a same-origin rewrite so the browser never sees a cross-site request at all — sidestepping the cookie problem entirely instead of fighting it with CORS configuration. CI runs on GitHub Actions with JUnit 5, Mockito, and Testcontainers-backed integration tests, with JaCoCo coverage reporting.

## Results

A fully working, publicly deployed application: a user can register, configure their spending preferences, submit a transaction, and get back a real-time decision with an explanation of exactly which rules contributed to the risk score — backed by a real layered architecture (controller → service → repository → entity, with DTOs and mappers at the boundary, a modular Strategy-pattern rule engine, and a dedicated audit trail) instead of a single package of tangled logic. An admin can view and manage users, adjust rule weights without a redeploy, and review a complete audit log of every sensitive action in the system. The entire stack — backend, database, and frontend — runs on free infrastructure with a real CI pipeline gating it.

## What Broke

The most useful part of this project wasn't what went right — it was diagnosing what went wrong, since every failure traced back to a real, explainable cause rather than a mystery:

- **Flyway silently didn't run.** The first Docker deploy failed with Hibernate reporting a "missing table" error that looked like one missing table but was actually an entirely empty schema — Flyway migrations weren't wired into the build at all yet, since the dependency wasn't in `pom.xml`. Once that was fixed, a second, different failure hit on the actual Render deploy: `Unknown database 'impulselock'` — Flyway was working correctly this time, but the JDBC URL assumed a custom database name that Aiven's free tier doesn't allow (it provisions one fixed database, `defaultdb`, that you don't get to rename).
- **A CI test was flaky by construction, not by luck.** An admin integration test asserted a fixed count of users in the system and failed intermittently depending on what other tests had run first — a textbook test-isolation bug where earlier tests' created data leaked across test boundaries instead of being cleaned up.
- **Two deploy paths silently disagreed with each other.** Render's own GitHub auto-deploy fires on every push regardless of test results, while a separate GitHub Actions "deploy" job was gated behind CI passing — meaning a "protected" deploy pipeline could be quietly bypassed by an entirely different, ungated one shipping the same commit anyway.
- **Cross-origin cookies would have broken auth in production** the moment frontend and backend lived on different domains (Vercel and Render) — a `SameSite=Strict` refresh-token cookie simply never reaches the server across origins, which would have logged every user out the instant their short-lived access token expired.
- **Free-tier cold starts read as bugs.** Render spins a free instance down after 15 minutes idle and can take 50+ seconds to wake back up — the frontend's request timeout was shorter than that, so a real user's first request after any idle period surfaced as a generic "Request timed out" error that looked like the app was broken rather than just asleep.

## Stack

**Backend:** Java 17, Spring Boot, Spring Security (JWT, BCrypt, role-based access control), Spring Data JPA / Hibernate, Flyway, MapStruct, springdoc-openapi (Swagger/OpenAPI), JUnit 5, Mockito, Testcontainers, JaCoCo

**Frontend:** React

**Database:** MySQL (Aiven, free tier)

**DevOps:** Docker, Docker Compose, GitHub Actions (CI)

**Deployment:** Render (backend), Vercel (frontend), Aiven (managed MySQL)
